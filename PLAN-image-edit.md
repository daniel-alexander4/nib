**Glossary (plan-review pin: consistency, 2026-11-06).** *Object* = a picture or a drawing. *Edit Objects* is the literal menu label. The door refuses; the window shows the refusal's `Why`. The window's verb is **Remove from page**, never "Delete" (see D3's wording pin). Decisions below carry the date of this plan (2026-11-06) unless a pin says otherwise.

Nib edits text (Edit text, reflow, ADR-071/155) and adds stamps and pictures, but cannot select a picture or a drawing the page already draws and delete, move, resize or replace it. Acrobat, Foxit, PDF-XChange, Xodo PDF Studio and PDFgear can (README comparison table, *Where the others are stronger*).

## Repo laws this plan stands under

- **L1. One door writes page content** (ADR-009, ADR-056, ADR-129). A page object is edited through `pdfops.EditPageObjects` and nothing else; the server, the CLI and the window never build content bytes. A guard names the door.
- **L2. An edit acts on the object that was shown** (ADR-001, ADR-146). The window names an object by an address from a read; the write re-reads the page and refuses an address that no longer names the same operator. Never act on position alone.
- **L3. Nothing claims what it did not verify** (ADR-031, ADR-032). Every edit drops a PDF/UA identification inside the rewrite it already performs (`writeMutated`); a tagged document's structure is never left describing content that is gone.
- **L4. A signed document is not edited** (tagwrite's predicate, `tagwrite.go:29-48`; reflow `reflow.go:79-81`). The edit is refused at the door, not only greyed in the window.
- **L5. A page object that a form XObject draws is not edited here** (ADR-125's `InForm`). Editing the form changes every page that draws it.

## Decisions

Each is tagged by how it was reached: `auto-adopted` (correctness settled it), `assumed` (a defensible judgment on Dan's behalf, to read), `Dan` (his call). Facts below were read in the source on 2026-11-06; `file:line` are pointers to re-read at slice-grill time.

### D1 — One reader returns every object, owned or not, with an address *(auto-adopted)*
`readPageDrawings` (`textrun.go:307`) already keeps each image's own operator span (`drawnImage.span`, "`Do` with its operand, or the whole of `BI … EI`", `flowregion.go:86-90`), its box, `inForm`, `artifact`, `marked`, `objNr`, `clipped`, `translucent` and draw order. `ReadUntagged` lists only unowned pieces and cannot be the reader for this: a picture inside a Figure is exactly what a person wants to delete. A new reader `ReadPageObjects(pdf, page)` over the same walk returns every picture (later every drawing, via `groupUnowned`'s grouping) with the flags above and `Editable`/`Why`.

**(plan-review pin: one door, 2026-11-06)** `ReadPageObjects` is the ONE reader of `pr.images` for listing: `untaggedPieces`/`ReadUntagged` derive their image rows from it, and one function `objectEditability(img, tree)` owns `Editable` and every `Why` (the same strings are the refusal causes). Observed by a census, `TestEveryImageListingRoutesThroughReadPageObjects`, red on a second reader of `pr.images`, with a mutation row. **(plan-review pin: bounds, 2026-11-06)** The walker's image list is bounded: a named ceiling, a time and byte ceiling measured at 10,000 images with 10,000 DISTINCT names/digests, and a named refusal past it (a count and the cap, never a silent truncation). The fixture also includes a seeded duplicate-digest page (see D2). **(plan-review pin: placement fields, 2026-11-06)** The object carries `placeSpan` (the preceding `cm`, or none) and the `q` nesting count from P01.S01, so P02 reuses the field and does not re-version the address (D8). Types crossing to `web/app.js` have their JSON tags fixed in the slice, not left open: digest a hex string, ordinal an int, box `[4]float64` fractions; a jsdom contract test round-trips a value above 2^53.

### D2 — An address is (page, draw-order ordinal, operator digest) *(auto-adopted)*
An ordinal alone shifts when anything before it is edited; a span alone shifts when a rewrite moves bytes. The write re-reads the page, finds the ordinal's object and compares the digest of its operator bytes (`Do` plus operand name, or the whole inline image) to the one it was given; a mismatch is 409 `object-changed` (ADR-146's way back is a reload). The request also carries `baseRev` like every posted operation.

**(plan-review pin: the address, 2026-11-06)** The ordinal is the **image-only index among `pageRuns.images`** from the new reader's own walk, never `seq` (`w.draws` counts runs, images and, only under `keepShapes`, shapes: `textrun.go:1514`, `pageshape.go:136`, `flowregion.go:95`, so `readPageDrawings` and `MapPage` number one picture differently). The window selects by the index and box it was handed and never recomputes one from the page map or pdf.js. The digest covers the operator bytes plus the preceding `cm` and the `q` depth, so two identical `Do`s stay distinct. The server takes the span from its own re-read and **never accepts one**, and re-derives `inForm` itself, refusing before any `Edit` is built (a form Do'd twice gives two records with one span). `baseRev` is **required** from the window (the CLI takes a page-stream digest as its precondition instead); the route snapshots `docBytes` once, edits that snapshot, and commits with the snapshot base, parsing outside `s.mu` as `fateOf` does. Several objects in one request: sort spans descending, reject overlap, verify every digest against the re-read before any `Replace`. After the write the door re-reads and requires exactly one fewer image per removed object and an equal text-run count, else it refuses `rewrite-differs` and leaves the document untouched. Observed by: a test that the index is identical with and without `keepShapes`; a two-identical-`Do` page where a right-digest/wrong-ordinal request is refused; a form Do'd twice; a two-pictures-in-one-request fixture; a `/Contents` array fixture.

### D3 — Delete removes the painting operator and nothing around it *(assumed; proven by the S01 probe before S02 builds on it)*
`q … cm /Im0 Do Q` becomes `q … cm  Q`: the state operators stay, so the stream stays balanced whatever surrounds the picture, and draw order of everything else is untouched. This avoids the one thing `drawingBrackets.around` (`claimtagging.go:315-340`) exists to handle (pdfcpu ends an inline image only at `EI`+space+`Q`) because the whole inline image is removed. The edit is `contentstream.Edit.Replace(span.start, span.end, nil)` then `setPageContent` (`tagemit.go:79`), the pair `region` already uses (`structregion.go:262-267`). The assumption to falsify: a page whose stream, once an operator is removed, pdfcpu's relaxed validator or a viewer reads differently. S01 measures that over the local corpora before any route exists.

**(plan-review pin: header, 2026-11-06)** Stage 2 already ran this probe once (below); the header reads "assumed, measured at Stage 2 (1,633 of 1,635 clean); S01 re-runs it as the committed instrument with a rendered comparison and the checker added".

**(plan-review pin: what delete does to the file, 2026-11-06)** Removing the `Do` does not by itself remove the image from the file: the per-page resource prune (`pdfread/optimize.go`, `ReadOptimized`) runs at READ, before the edit, so `/Resources /XObject /ImN` still names the image when it is written, and `pdfread.Write` writes by reachability. **This reading is from the source and has not been run; S01 decides it** by counting the image's bytes extractable from the output. The remedy, **unverified until S01 runs it**: after the content edit, remove the `/XObject` entry only when a re-walk of every page, form, pattern, Type 3 font and annotation appearance finds no operator naming it (a shared `/Resources` dictionary and a name drawn twice are the hostile cases), remove an `/SMask` partner that nothing else uses, and drop the page's `/Thumb` in the same rewrite. Link annotations whose `/Rect` lies inside the picture's box are counted in the answer and never removed silently. A picture another page or form still draws is kept and the answer carries `SharedWith`. **If the prune cannot be made to hold, the edit is declared as hiding and not removing.** Either way the window's and CLI's verb is **Remove from page**, and no wording claims the file no longer holds the picture; the status line says "Undo brings it back until you close this document" and points at Redact when the data must go (README's crop wording is the precedent). Observation that discharges this pin on its own: a test in the shape of `TestRedactionLeavesNothingOnlyTheRedactedPageDrew` that plants a unique byte pattern in the image and asserts it absent from every decoded byte after the edit, mutation-red against switching the prune off, plus a second case where the image survives because another page draws it.

**(plan-review pin: hostile streams, 2026-11-06)** S01's fixtures add: `W n` before `Do` inside and outside `q`; an unbalanced `Q`; a `cm` with no `q`; a picture that is the only content of a `BDC…EMC` pair; an inline image whose neighbours fall outside `q cm … Q` (reader marks it not editable with a named cause and does not rely on the deletion); a `/Contents` array split between `/ImN` and `Do` and between `BI` and `EI` (spans from `pdfread.PageContent`, the door `structregion.go` uses); a shared `/Resources` dictionary across two pages. Oracle: later objects' boxes unchanged before and after. Pictures in annotation appearances, patterns, Type 3 glyphs and soft-mask groups are listed as "not editable" with a cause.

### D4 — A picture inside a tagged sequence takes its structure with it, or the edit refuses *(assumed)*
A `marked` image sits inside `/P <</MCID n>> BDC … EMC`. Deleting only its `Do` leaves an empty marked-content sequence and a Figure element whose content is gone, which the PDF/UA checker and a screen reader both read as a defect Nib wrote. So: P01.S02 refuses a `marked` object (`Why: "tagged"`) where its Figure holds other content; P01.S02 (the old P01.S03 absorbed) makes the rest work by removing the element's reference to that content through ADR-124's `delete` when the Figure holds only this content, and by refusing when the element holds other content. Nothing is left describing what is not drawn (L3).

**(plan-review pin: one rewrite, 2026-11-06)** Coordinates now read: P01.S02 absorbs the old P01.S03, because the content edit and the structure edit must be ONE rewrite (a second write can land after a signature or break convene's mirror, ADR-032). The operator removal, the `BDC…EMC` bracket, the `/ParentTree` slot, the `/K` entry, the `/IDTree` entry and the element go together or the object is refused. ADR-124's own refusals (a top-level element holding content, the last element, one inside an inline element) are expected causes with plain wording; the last-element case points at removing all tags (`structcreate.go:111`). An object under an `/Artifact` sequence is distinguished from a marked one: it deletes without the description warning. A Figure with `/Alt` warns in the window that its description is removed with it.

### D5 — The signed-document refusal is the shared predicate *(auto-adopted)*
`tagwrite.ErrSigned` / `sign.HasSignatureBlob` is "the one door for is-this-signed" (`reflow.go:79-81`). The new door calls it. A new route is caught by `TestEveryStructureWriteReachesTheSignedDocumentDoor`'s shape; this plan adds the same census for content edits.

**(plan-review pin: the signed door, 2026-11-06)** `EditPageObjects` is itself the signed-document door: `sign.HasSignatureBlob` is checked **before any read**, so the CLI cannot reach an edit without it. Observed by a route test and a CLI test on a signed fixture, and the census in S02. **(plan-review pin: ceremony record, 2026-11-06)** A document that carries a ceremony record is refused with cause `ceremony`, read through the embedded record (`ceremony.Extract`; an unreadable record, `ErrRecordUnreadable` or `ErrNameTreeLost`, also refuses). It is NOT keyed on `doc.ceremony` (set only by convene and by `installCeremonyResult`, `server.go:871-876`, so a reopened ceremony file would pass) and NOT on `hasLiveCeremony` (machine-wide). Reason: while a document is unsigned the arrival gate recomputes `DocumentHashFor` against `rec.DocHash` (`ceremonyid.go:855-900`), and an edit would make every counterpart refuse it as substituted. The words say so: "This document is part of a signing ceremony; edit before you start one." Observed by a test that convenes, deletes through the door and expects a 4xx `ceremony`, and by a second test that reopens the convened file cold. Whether a `/Perms` certification signature counts as `HasSignatureBlob` is tested in S02, not assumed.

**(plan-review pin: where the door lives, 2026-11-06 second pass, amends the two pins above)** `EditPageObjects` is NOT the signed door and cannot be: `pdfops` imports neither `sign` nor `ceremony` (`go list -deps ./pdfops`; `tagwrite.go:14-17` gives the cycle for `sign`, and `ceremony` imports `pdfops` at `ceremony/embed.go:10`). So `pdfops.EditPageObjects` is the pure content writer, and the signed refusal (`sign.HasSignatureBlob`, **before any read**) and the ceremony-record refusal live in a wrapper package in `tagwrite`'s shape, which imports `pdfops`, `sign` and `ceremony`; the server and the CLI call only the wrapper, and the S02 census's routing half asserts it. Form-drawn re-derivation stays in `pdfops`. `ceremony.Extract` answering "no record" (`ErrNoRecord`) proceeds; an unreadable record refuses. The refusal does not ask whether a ceremony is live: a convened, unsigned document is refused cold. **Unverified:** the wrapper's own imports are not compiled yet; the slice's first task compiles an empty wrapper package importing the three before anything is built on it.

### D6 — The window selects with a click and acts with a button or the Delete key *(assumed)*
ADR-125 refused a dragged-rectangle path ("a twelfth placement tool"); clicking a picture is not placement. ADR-105 puts a tool that acts on the open document in the menu: **Page Functions → Edit Objects**, one `.tbgroup[data-entry]` button in the existing group, armed-tool chip as the other tools. The hit-test reads the page map (`GET /api/pagemap`, `web/app.js:16010`) plus the new objects read; no pdf.js annotation editor is used (`web/app.js:13919`), because these are page content, not annotations.

**(plan-review pin: cost, 2026-11-06)** Hover and move call the server never: the window reads a page's objects once per (doc id, page, `rev`), caches them, hit-tests the cache on click, and drops the cache on a `rev` change (`/api/pagemap` and `ReadUntagged` are each a full pdfcpu parse). Observed by a jsdom test that counts fetches. **(plan-review pin: keyboard and announcements, 2026-11-06)** One roving-tabindex group with a single Tab stop and arrow keys inside it, Escape leaves it; each object is named "Picture N of M, page P" plus its `/Alt` when it has one. Remove-from-page is bound to the FOCUSED object element only (`ev.target === el`, `!defaultPrevented`, ignoring input and contenteditable targets); the existing Delete handlers (`web/app.js` near 8920, 14204, 14572 are unguarded) are read at slice-grill. Selection and refusal both write one polite region (the `#importNotice` pattern, ADR-186), not the status line alone. The outline is two-tone at 3:1 or better against any backdrop. Observed by jsdom tests that press the key with a stamp selected and with a picture selected and see exactly one thing removed, and that read the region text.

### D7 — Undo is the document's own install history *(auto-adopted)*
The edit installs through `document.install` (ADR-146) so Undo/Redo and the global history budget (ADR-003) apply unchanged. No second undo.

**(plan-review pin: history cost, 2026-11-06)** One edit installs a full-document history entry and `maxUndoBytes` is 256 MiB (`server/undo.go:40`), so a document above about 128 MiB cannot keep an undo/redo pair, and ADR-003 can drop an inactive tab's history whole. "Undo restores it" is therefore true only within that budget: the answer reports an evicted history through the existing `historyEvicted` path and the Undo control is disabled with its reason, not hidden. S02 measures bytes per edit on the large-scan corpus and states the figure; the door takes a LIST of edits so a multi-select is one commit. Undo after Save is tested.

### D8 — Move and resize rewrite the `cm` that places the picture, and refuse where it cannot *(assumed)*
The picture is the unit square under the CTM, so a move or resize is a new matrix. It is rewritten only where one `cm` sits straight before the `Do` inside the same `q … Q` (the `drawingBrackets` shape, `claimtagging.go:312-314`). A nested or composite placement, a form-drawn picture (L5), a rotated or sheared picture in P02.S01, and any picture another object's clip depends on are refused with a named cause. Nothing is "approximately moved".

**(plan-review pin: placement, 2026-11-06)** Rotated and sheared pictures are classified in P02.S01's reader and refused in the door (P02.S01 as now merged). A `cm` is cumulative: a placement is editable only when the `cm` and `Do` sit inside a `q`/`Q` that holds nothing else that draws, and the door re-verifies that at write time (`1 0 0 1 100 200 cm /Im0 Do /Im1 Do` must refuse, as must a `cm` outside any `q`). There is ONE conversion from displayed fractions to the new `cm`, covered by fixtures with `/Rotate` 90/180/270, a non-zero CropBox origin and `/UserUnit`; each term is mutation-red. The address already carries `placeSpan` (D1's pin).

### D9 — Replace uses the one import function and keeps the structure element *(assumed)*
A replacement picture arrives as a file; `pdfops.Import` is the one door a non-PDF becomes a PDF through (ADR-185), so the new picture is imported to a one-page PDF and its image XObject is taken from that, never decoded by a second reader. The old image is removed (D3), the new is drawn at the old box, and a tagged Figure keeps its element and `/Alt` (D4). The image library in the vault (`/api/images`) is a stamp library and is not the source.

**(plan-review pin: replace bounds, 2026-11-06)** Replace accepts a named raster allowlist taken from the format table (not "anything `Import` takes": an `.svg` or `.docx` would start an outside tool), has its own body cap and decoded-pixel ceiling, runs under ADR-008's byte cap (409), and uses `internal/tempdir` and the gate as `Import` does. The ADR-185 and ADR-187 census tests name the new caller, and no second image decoder is added. The old image is pruned by D3's pin or the new one doubles in the file.

### D10 — Vector drawings last, grouped as ADR-125 groups them *(assumed)*
`groupUnowned` (`grouping.go:474`) is the grouping door: paths whose boxes touch are one drawing. P03 offers a drawing as one object to delete and move; it never splits a path and never joins through a plain box that holds the other whole (ADR-125). A drawing inside an `/Artifact` sequence is whole-sequence or refused, as `region` does. **(plan-review pin: forms, 2026-11-06)** A form-drawn drawing is refused by L5, in the reader and in the door, as a picture is; P03's exit criteria carry it. `ReadPageObjects` is the one caller of `groupUnowned` for object addresses; P03.S03 says how a drawing's ordinal is renumbered after a delete, because the grouping can merge differently once a path is gone.

## Build order

### P01 — Delete one picture
Goal: select a picture the page draws and remove it from the page, safely, on an untagged, then a tagged, document.
Exit criteria: a picture on an untagged page is removed from the window and Undo restores it; a Figure's picture is removed with its element or refused with a named cause; a signed, ceremony or form-drawn page is refused; `nib` has the same operation on the command line; the corpus probe shows no page read differently by pdfcpu or the checker.

#### P01.S01 — The objects reader and the delete probe
Scope: `ReadPageObjects` for pictures (D1, D2), and an instrument that deletes each picture of each corpus page in memory and compares what pdfcpu and the checker read before and after (D3's falsification). No route, no window. Refs: D1, D2, D3, L1, L2.
Acceptance:
- The reader returns every image of a page with address, box fractions (the page map's space, ADR-088), `Editable` and a `Why` for each refusal (form-drawn, tagged where its Figure holds other content, signed).
- `build/` instrument (local list, counts only, like `formshape.sh`) prints how many pictures were deleted cleanly and how many pages read differently afterwards; any difference is a finding that changes D3 before S02.
- Hostile fixtures: inline image, image in a form, image under an `/Artifact` sequence, image with a soft mask, a page whose `/Contents` is an array, 10,000 images (cost measured, not argued).
- *(plan-review pin: oracle, 2026-11-06)* The instrument identifies WHICH object was removed and not only how many: after the edit the surviving operator digests equal the original list minus exactly the addressed one, in order. It also renders the page before and after (`pdftoppm -r 72`; renderer and per-channel tolerance written in the slice): pixels inside the deleted box change, pixels outside stay within the tolerance. A seeded wrong-ordinal edit must make it report red. It runs the PDF/UA checker before and after, not pdfcpu's re-read alone.
- *(plan-review pin: population, 2026-11-06)* The instrument exits non-zero (a third verdict) when it reads fewer than a declared minimum of pictures (1,000), because its lists are local and a fresh clone would pass over nothing; a tier-1 test runs the same code path over a committed hostile-fixture set with a floor on pictures found. Counts are reported separately for edited, form-drawn, tagged and not-rewritable (a document that fails the no-op rewrite control is "not editable", per Stage 2).
- *(plan-review pin: file residue, 2026-11-06)* The instrument measures, for every deletion, whether the picture's bytes are extractable from the output (`ExtractPageImages`) and the file's byte change; this answers D3's file-residue pin before S02 is built.

## Stage 2 — recon of the load-bearing claims *(run 2026-11-06)*

**D3 (delete the painting operator only) was measured, not argued.** A throwaway probe (never committed) took every picture of the first two pages of each local-corpus document (first two pictures a page), removed its recorded span with `contentstream.Edit.Replace`, wrote through `setPageContent` and `pdfread.Write`, re-read the result and compared. Population: the four local lists (`accuracy`, `formrt`, `export`, `population`), 2,165 listed, 2,159 documents read (15 unreadable), 3,437 pages, 1,814 pictures, of which 179 are drawn by a form (refused by L5, not edited) and 236 are tagged (edited at the byte level to test the stream; D4 is about their structure).

| Result | Count |
|---|---|
| deleted, re-read by pdfcpu, one picture fewer on the page, page text-run count unchanged | 1,633 |
| write or re-read failed | 2 (one document, page 1, both pictures) |
| re-read with the wrong number of pictures | 0 |
| page text-run count changed | 0 |

**The two failures are the document, not the deletion.** A control that rewrites the same document with the page's content unchanged (`setPageContent` with the original bytes) fails to re-read in exactly the same way. A document that does not survive a rewrite through this path is a separate defect, and S01's instrument counts such documents as "not editable" rather than as delete failures.

**What this does not show.** It is 1,633 deletions on one machine's files, the first two pages and two pictures a page; it is not every picture. It checks pdfcpu's reading and the page's text-run count, not a rendered comparison, not the PDF/UA checker and not a viewer other than pdfcpu. It says nothing about a tagged picture's structure (D4) or about moving a picture (D8). S01 re-runs it as the committed instrument with a rendered comparison added.
